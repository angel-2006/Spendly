# Spec: Login and Logout

## Overview
Make sign-in work. Today `GET /login` only renders a form that posts nowhere, and `/logout` is a stub string. This step adds `POST /login`, which looks up the user by email, verifies the password against the stored werkzeug hash, and stores the user's id in the Flask session. It also implements `/logout`, which clears the session. This is the first step that introduces sessions, and it is the foundation for every logged-in page (profile, expenses) in later steps.

## Depends on
- Step 1 — Database setup (`users` table, `get_db()`).
- Step 2 — Registration (`get_user_by_email()`, users with hashed passwords, redirect to `login`).

## Routes
- `GET /login` — render the login form (already implemented); if already logged in, redirect to `landing` — public
- `POST /login` — validate input, verify credentials, set `session["user_id"]`, redirect to `landing`; re-render `login.html` with an error on failure — public
- `GET /logout` — clear the session and redirect to `landing` — public (safe to call when not logged in)

The `login` view function handles both methods via `methods=["GET", "POST"]`.

`/profile` is still a stub (Step 4), so a successful login redirects to `landing` rather than `profile`. Do not implement `/profile` here.

## Database changes
No database changes. The `users` table already has everything needed.

New helper in `database/db.py` (DB logic must not live in the route):
- `get_user_by_id(user_id)` — return the matching `sqlite3.Row` or `None`. Used to load the current user's name for the navbar.

`get_user_by_email()` already exists and is reused for credential lookup.

## Templates
- **Create:** none
- **Modify:**
  - `templates/login.html`
    - Change `action="/login"` to `action="{{ url_for('login') }}"`.
    - Re-populate the `email` field after a failed submission. Never re-populate the password.
    - Keep the existing `{% if error %}` block.
  - `templates/base.html`
    - Navbar is session-aware. Logged out: "Sign in" and "Get started" (as today). Logged in: show the user's name and a "Sign out" link to `url_for('logout')`.
    - Uses a `current_user` template variable supplied by a context processor (see below), not DB calls in the template.

## New dependencies
No new dependencies. `werkzeug.security.check_password_hash` ships with Flask's existing dependency.

## Session and secret key
- `app.secret_key` is read from the `SECRET_KEY` environment variable, with a clearly-labelled development fallback string so `python app.py` works out of the box. Do not commit a real secret.
- Store only `session["user_id"]` (an int). Never store the password or hash in the session.
- On successful login call `session.clear()` before setting `user_id` to avoid session fixation.

## Validation rules
Applied in `POST /login`, in this order. Any failure re-renders the form with HTTP 200 and an error.
1. `email` — strip whitespace and lowercase (same normalisation as registration); required.
2. `password` — required.
3. Look up the user with `get_user_by_email()` and verify with `check_password_hash`. If the user does not exist **or** the password is wrong, show the same generic message: "Invalid email or password." Never reveal which part was wrong.

On success: set the session and `redirect(url_for("landing"))`.

## Rules for implementation
- No SQLAlchemy or ORMs
- Parameterised queries only — never f-strings in SQL
- Passwords hashed with werkzeug; verify with `check_password_hash`, never compare plaintext or hashes directly
- Use CSS variables — never hardcode hex values
- All templates extend `base.html`
- DB logic lives in `database/db.py` only; routes read the form, call helpers, and render or redirect
- Use `url_for()` for every internal link and redirect
- Do not implement any other stub route (`/profile`, `/expenses/...`) in this step
- Do not change the port (5001)
- Use `abort()` for HTTP errors, not raw strings
- No new pip packages (no Flask-Login); use Flask's built-in `session`
